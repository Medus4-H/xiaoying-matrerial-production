# 本地多站点会话隔离计划

目标：默认 Compose 项目按站点端口隔离用户及访客备份 Cookie；保留有效的旧会话与已有资料，不重置数据库或素材卷。

1. 为各端口产生独立的 Cookie 名；保留显式配置能力，并同步基础检查脚本的预期名称。
2. 当前站点不存在新 Cookie 时，仅在本数据库验证旧 Cookie 后迁移原会话与可验证的访客备份；旧 Cookie 不删除、不覆盖。已存在新 Cookie 时不使用旧 Cookie 代替。
3. 用 MySQL 集成测试覆盖有效和无效旧会话、迁移后的个人资料、访客备份以及新会话优先级；用独立双站环境验证切换、刷新、跨站访问、容器重建和保留数据。
4. 不尝试猜测或找回已被覆盖、过期或清除的匿名 Cookie；实事求是记录限制。
5. 容器内执行前后端检查，逐项复核 R-01 至 R-14，记录本次运行证据和工时边界；验证无误后再提交和推送。

## 2026-10-29 验证记录

- 代码验收基线：`25233dc5551b7b6e24d0423db9350829fcdb8943`。
- Compose 按配置的前缀和 `FRONTEND_PORT` 生成用户会话名称；旧名称迁移只在目标数据库验证有效、新名称和迁移标记均不存在时进行，旧主 Cookie 不被删除或覆盖。账号的有效旧访客备份也会迁移；站点标记防止退出后意外回退旧身份，诊断会话使用各站点独立名称。
- 隔离 MySQL 集成测试覆盖有效旧会话、旧素材归属、新会话优先、无效旧会话、无效新会话不回退、POST 建立会话迁移、账号访客备份恢复和退出后不回退。Java `verify` 共 27 个单元测试和 53 个集成测试通过，含格式检查和构建；前端 62 个 Vitest、4 个 Node 测试、lint、类型、格式及构建通过。
- 两个新 Compose 项目通过真实 Next.js 代理和 Java 接口运行 [双站隔离检查](../checks/session-sites.mjs)：同一个模拟 Cookie 容器先迁移有效旧会话，再交替建立两个站点的素材和任务，反复切换后验证身份、历史、结果及跨站 404；还验证了旧账号与访客备份通过代理同时迁移，退出后恢复访客及其任务。该检查使用项目自带素材进行接口验证，**不代表浏览器上传验收**。
- 原账号隔离接口脚本使用固定邮箱，重复运行会因已有测试账号返回 409；已改用每次运行的独立测试邮箱，并在新库及同一测试库重复运行验证通过。它仍只可用于独立演示环境。
- 在同一个应用内浏览器中交替打开并刷新两个独立测试站点，各站点访客身份保持一致；未做带任务的浏览器上传、切换和刷新验收。原 3534 验收站的有效旧访客会话升级后仍可识别。
- 应用到现有 3000 主站和 3534 验收站之前，分别检查无排队或运行中任务；只重建后端容器，未重建数据库或素材卷。应用前后主站的任务状态分布及素材计数一致；该计数证明数据未因这次操作减少，不证明任意原访客 Cookie 都仍然存在。
- 本次修复不会找回之前已经丢失、清除或过期的匿名访客 Cookie；注册账号可重新登录。若主动更换端口或 Cookie 前缀，需要按 README 配置旧 Cookie 名以迁移尚存的会话。
- 工作流已加入双站接口隔离检查；GitHub 托管 Actions 此前被账号级禁用，新增工作流是否在托管环境运行仍未验证。
