# Task 4：后台任务实施与验证记录

日期：2026-10-28。范围是 Java 后端任务接口和模拟处理；页面上传、任务轮询、历史和结果展示属于后续 Task 6、7。

## 已实现

1. `POST /api/tasks` 校验访客、来源、模板、素材归属与数量、类型、大小、模拟参数；在数据库事务中创建任务、素材关联和三个步骤，事务提交后向线程池派发，返回 HTTP 202 和任务快照。
2. Java 使用有界线程池按「素材检查 → 模拟生成 → 结果整理」顺序执行，每一步分别持久化开始和结束；失败记录阶段及原因，并跳过后续步骤。素材检查再次验证素材。查询接口仅读取已持久化状态。
3. 模拟生成复制随项目提供的预置 JPEG，结果整理发布任务专属图片；这可以演示异步流程，但不是 AI 生成，也不依据上传图片修改内容。
4. 按访客提供任务详情、全部未结束任务、分页历史和结果图片接口；他人的任务或结果返回 404。支持历史按模板筛选。
5. demo 模式下可通过请求指定某个阶段失败、调整各阶段耗时；prod 模式不允许请求覆盖模拟参数。创建任务时保存模板要求和模拟参数快照。
6. 默认并发 2、队列容量 20，均可配置。队列满时任务记录会标记为 `FAILED/DISPATCH_REJECTED`，接口仍返回 202 和该任务；须以快照状态判断结果。
7. 单实例后端启动时将遗留的等待中和处理中任务标记为 `FAILED/SERVER_RESTARTED`，不会重新执行；已执行的阶段保留，未执行的阶段跳过。

接口字段、示例及状态枚举见 [接口文档](./api.md)；环境变量见根目录 `.env.example` 和 [README](../README.md)。线程池参数或全局阶段耗时修改后需重新创建后端容器；每个已受理任务保持自己的参数快照。

## 验证记录

- `docker compose -f compose.check.yml run --build --rm backend-check`：Java 格式检查、打包、10 项单元测试和 11 项 MySQL 集成测试通过。覆盖执行顺序、各阶段失败及停止后续步骤、重复领取、参数验证、结果和用户隔离、队列拒绝、prod 限制及启动收尾逻辑。
- 在独立 Compose 项目中将 `TASK_CONCURRENCY` 设为 1、`TASK_QUEUE_CAPACITY` 设为 3，执行 `docker compose --profile tools run --rm task-check` 对同源代理进行真实请求检查：两个任务互不影响、受理后仍可查询、三个阶段各自可复现失败、历史和结果可读、另一访客不能读取，通过。该检查会创建演示访客、素材及任务，应仅在隔离演示环境使用，且需要 demo 模式。
- 真实重启验收：在独立 Compose 项目里将阶段耗时上限设为 120 秒、创建正在执行的任务，强制终止并重启后端；通过原访客查询确认任务为 FAILED/SERVER_RESTARTED，当前步骤 FAILED、后续步骤 SKIPPED，未续跑。验收脚本为 checks/task-restart.mjs，需要独立环境和交互式停止/重启。
- CI 配置已加入上述任务接口检查；GitHub 托管流水线尚未实际运行。前端的多任务、查询异常、页面生命周期和刷新恢复尚未实现或验证。

## 设计边界

- 队列在应用内存中，不支持多实例或重启恢复执行；创建记录和派发之间存在进程异常窗口，重启时将遗留任务标记失败。没有幂等、自动重试和断点续跑。
- 后端关闭时只在配置的时间内等待，未承诺队列一定排空。若数据库不可写，可能无法及时记录失败；文件与数据库不在同一个事务中，异常退出可能遗留文件。未引用素材暂不自动清理。
- 身份恢复是 TODO：当前匿名 Cookie 过期或清除后无法找回旧访客资料，不支持跨设备。按用户要求，本阶段不调整身份方案。
- 工时尚未精确计量，不把计划耗时写成实际投入；正式交付前需如实补充。
