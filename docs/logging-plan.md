## 1. 目标与范围

在现有素材制作网站上完成以下改造，并保留访客、账号、素材和任务的既有数据：

1. 建立可检索的请求与后台任务日志，能从请求编号定位提交与执行结果。
2. 集中管理错误码和错误文案，支持按语言解析，业务代码不散落字符串文案或错误码字面量。
3. 细分错误原因，在保护用户与资源信息的前提下，将需要长期保存的内部原因持久化。
4. 展示任务阶段耗时，提供可开关的 JVM、线程池和队列诊断指标。
5. 提供受控的本地开发诊断页面，并对其权限、暴露范围及保留策略做明确限制。
6. 补齐自动测试、容器验收、配置示例与 README。

以上是本次总体目标，完成情况以阶段记录为准。分阶段描述的是依赖和实施顺序，并不表示后面的目标被取消。错误码、响应、数据库字段及诊断页面会改变现有接口和功能，应分别验证兼容性。

本题原始要求不包含完整国际化、日志后台或性能监控；这是用户提出的扩展。预计会明显增加三天笔试的工作量，工时在第 10 节单独说明。暂不建设 ELK/Loki 等外部聚合平台、生产级管理后台或全站多语言切换；错误文案国际化与全站国际化是不同范围。

## 2. 改造前的实现与参考

- 后端使用 Spring Boot、MyBatis 和 MySQL；前端为 Next.js。当前 `ApiException` 构造时同时传错误码及中文文案，业务中存在重复字符串。
- `ApiError` 带 `code`、`message`、`fieldErrors`、`requestId`。未知 500 的 requestId 当前已经同时出现在响应和错误日志中；其他业务错误的编号没有统一贯穿日志。前端 `ApiError` 当前未保留 requestId。
- 任务及步骤已有 `error_code`、`error_message`、开始和结束时间。详情页已有阶段状态与失败文案，但没有显示耗时。
- 任务执行由线程池异步完成；任务提交事务结束后派发。队列拒绝时会创建失败任务，提交接口仍返回 202，不能将 HTTP 202 等同于成功派发。
- 重启时未完成任务标记为失败，不支持自动续跑。
- 邮箱与手机号在身份接口已脱敏，但数据库仍保存原值；日志不能因此认为这些数据可随意记录。
- 现有 R-xx 功能、自动化测试和容器检查有不同程度的实现与验证；不要把源码实现等同于全部验收完成。README 中的真实工时和 CI 实际触发情况仍应如实记录。

## 3. 错误码与 i18n 设计

### 3.1 分层与单一来源

| 概念 | 用途 | 是否给用户 |
| --- | --- | --- |
| `code` | 稳定业务语义与前端分支判断，例如 `LOGIN_FAILED` | 可以，接口兼容保留；界面默认不展示 |
| `messageKey` | 面向用户的安全文案键，例如 `asset.type_mismatch` | 可以；必须来自白名单 |
| `detail` | 内部原因，例如 `ASSET_NOT_OWNED` 或 `BAD_PASSWORD` | 仅后端日志及受控诊断，不从个人任务接口透出 |
| `message` | 根据文案键解析出的安全兜底文案 | 可以；兼容既有客户端 |

拟在后端资源中维护一个版本化的错误目录（例如 `backend/src/main/resources/error-catalog.json`），每项明确稳定 `code`、HTTP 状态、可公开的 `messageKey`、中文／英文文案、允许的参数和描述。内部 `detail` 单独维护在同一领域目录或其独立章节，禁止直接将内部原因用作用户文案。

- 中文为默认及最终安全兜底；英文作为验证 i18n 可用性的第二套错误文案。此范围只覆盖错误相关文案，不承诺整个网站均可切换语言。
- 根据目录生成或校验 Java 类型安全常量，并在 CI 中检查生成结果与目录一致；前端仅对需要分支处理的稳定 code 使用由同一目录生成的类型或常量，避免两边手抄漂移。
- 标识符必须在目录中有明确、稳定定义；“不硬编码”指**业务调用处不散落字面量、文案集中配置**，并不意味着错误码可以随机生成或随意改名。
- 模板参数只允许无敏感信息、类型与数量受限的明确字段；禁止把邮箱、手机号、文件名、堆栈、路径或原始输入传给翻译模板。
- 目录加载失败、缺少 key、缺少语言、参数不匹配时必须有可预测的安全兜底；不可直接展示未知异常原文。构建/测试阶段检查重复 code、缺少默认文案、翻译占位符不一致和非法状态码。

### 3.2 错误响应与语言选择

保留原有 `code`、`message`、`fieldErrors`、`requestId` 字段，按需新增可选 `messageKey` 和安全参数 `messageArgs`；不在本次改成 vergeX 的嵌套 `error` 结构。

```json
{
  "code": "INVALID_ASSET",
  "messageKey": "asset.type_mismatch",
  "messageArgs": {},
  "message": "图片类型与内容不一致",
  "fieldErrors": null,
  "requestId": "请求编号"
}
```

- 后端按受支持的 `Accept-Language` 解析 `message`，无匹配时回退中文；统一限制语言白名单，不从任意路径加载资源。
- Java 提供只读语言包接口（例如 `GET /api/i18n/errors?locale=zh-CN`），仅返回公开文案及版本；不返回内部 detail、异常信息或管理数据。使用明确的缓存策略，代码或翻译变更时更新版本。
- 前端统一错误解析：按当前语言的 `messageKey` 和安全参数解析，缺 key 时回退服务端安全 `message`，再回退前端内置的通用安全提示。语言包请求失败、服务不可用或无响应体仍可显示错误，不能把原始网络异常直接显示为业务原因。
- 当前没有全站语言设置；默认中文，可通过应用配置选择错误文案语言，测试验证中文、英文与不支持语言回退。后续若增加全站切换，再将它接入同一个语言状态。
- 会话失效、身份切换等前端业务分支仍按稳定 `code` 判断，不能按翻译文案判断。

### 3.3 错误细分与安全边界

先盘点现有 `ApiException`、`TaskExecutionException`、框架错误和前端错误分支，形成旧 code → 公开 messageKey → 内部 detail 映射。保留前端依赖的现有 code；同一个历史 code 若对应多个用户可理解的原因，用不同公开 `messageKey` 表达，不为了区分文案而破坏既有 code 分支。新增 code 需有明确版本兼容方案与测试。

| 场景 | 对外 | 内部 detail 示例 |
| --- | --- | --- |
| 登录失败 | 统一 `LOGIN_FAILED` 与“账号或密码不正确” | `UNKNOWN_IDENTIFIER`、`BAD_PASSWORD` |
| 素材不存在、无权访问、文件缺失 | 沿用统一的安全响应，避免资源枚举 | `ASSET_NOT_FOUND`、`ASSET_NOT_OWNED`、`ASSET_FILE_MISSING` |
| 图片格式、大小、像素校验 | 保留兼容 code；按具体规则返回安全 messageKey | `MIME_MISMATCH`、`DIMENSION_EXCEEDED` 等 |
| 后台检查、生成、整理 | 保留任务状态与稳定 errorCode，返回安全文案键 | 仅内部记录真实执行原因 |
| 未知异常或不可用 | 通用安全文案及 requestId（如果后端已经受理） | 异常类型与经审查的诊断信息 |

内部细分不应改变登录的对外统一语义。不要为了构造日志原因新增会改变认证行为的查询；如当前分支可判断原因，在不暴露账号的前提下记录。

### 3.4 任务历史与迁移

设计 V8 增量迁移，分别为 `tasks` 和 `task_steps` 增加可空字段，建议：

- `error_message_key`：用户可见的安全文案键；旧记录为 NULL。
- `error_message_args`：可空 JSON，仅存受控的非敏感参数；无参数时为 NULL。
- `error_detail`：受控内部原因，供后端诊断，不放进普通任务响应。

字段最终类型、长度、索引由迁移审查确定；当前没有明确的 detail 筛选需求，不预先添加索引。失败任务与步骤各自写入必要信息，状态转移及失败记录在既有事务边界内保持一致；不要仅为写日志而改变任务结果。

读取时优先按安全 key 和请求语言生成文案；旧记录没有 key 时保留其原有 `error_message` 作为兼容回退，并验证已存入的历史文案不会意外泄漏敏感信息。未知或不安全旧文案使用通用提示。保留原字段兼容旧版本；不要通过错误码猜测并批量重写历史数据。新版本回滚到旧版本时，旧版本应仍能读取原 `error_code/error_message`，迁移本身不自动回滚。

## 4. 结构化日志与链路

### 4.1 输出和字段

使用 Spring Boot 3.5 内置 ECS JSON 控制台输出，通过环境变量与配置文件控制开关和级别；不默认引入 JSON 编码依赖或额外日志平台。记录：`event`、时间、级别、`requestId`、`taskId`、`stage`、状态、耗时、稳定 code、允许的内部 detail，以及必要时的非敏感用户 ID。

- `requestId` 由服务端生成，并在响应头、错误体、请求日志中保持一致；不信任任意外部传入编号。若以后允许可信代理透传，必须校验格式、长度及信任边界。
- 在任务记录创建／派发事件同时记录 `requestId` 和 `taskId`；执行线程重新设置 `taskId` 和阶段，使用 `finally` 清理或恢复 MDC，避免线程复用导致串号。
- 对阶段耗时用单调时钟；数据库开始／结束时间用于历史展示。对于事务提交、派发拒绝、并发启动导致的事件顺序要如实命名：`task.created` 不代表已派发，`task.dispatched` 不代表已完成。
- 记录路由模板而不是原始 URL；不记录 query string、请求体、Cookie、凭据、验证码、邮箱、手机号、原始文件名、文件内容和本机路径。用户 ID、任务 ID 也应视为敏感关联标识，限制访问并设置保留策略。
- 不直接记录任意异常消息或 cause 链。可对受信任的异常类别记录有限堆栈，需过滤敏感数据和路径、限制长度；向用户返回通用信息。日志辅助逻辑失败不能改变业务状态或吞掉真实业务异常。

### 4.2 事件与降噪

- 身份：创建会话、账号注册／登录／绑定的成功和需要排查的失败；无 Cookie 的正常访客流程不统一记 WARN。
- 上传：成功、校验拒绝、存储或清理失败；记录大小、类型、尺寸，不记文件名。
- 任务：记录创建、派发成功或拒绝、领取失败、阶段开始／结束／失败、完成与清理失败。队列深度为采样值，不视作事务一致的精确队列历史。
- 重启：`task.interrupted_on_startup` 记录实际标记失败的数量，不命名为恢复执行。
- 查询：成功轮询、健康检查和静态资源默认不逐条记录；失败及超过可配置阈值的慢查询记录。避免同一异常在 Filter、handler、service 中重复记录完整堆栈。
- HTTP 查询日志与事件日志分别设置规则，确保“一次请求汇总”和“轮询降噪”不矛盾。过滤器内未被 MVC 处理、网络中断、Next.js 代理失败等情况单独说明；这些情况下不保证一定有后端 requestId。

## 5. 阶段耗时与运行指标

### 5.1 用户侧时间线

复用已返回的每步开始／结束时间，在任务详情显示阶段状态、已结束步骤的耗时和安全失败提示。进行中步骤、未开始、跳过、时间缺失或时间异常时展示合理占位，不显示负数；不要把内部 detail、任务 ID 或 JVM 指标展示给普通用户。此项为增强，现有状态与失败提示已具备基本展示。

### 5.2 诊断指标

- 默认记录阶段耗时、任务排队时长和线程池快照（队列深度、活动线程数）；队列和活动线程为采样值。
- 增加配置开关采样 JVM `heapUsed/heapCommitted/heapMax`、GC 累计次数与耗时；开关默认关闭，取样失败不影响制作任务。
- 如展示阶段前后 `heapDelta` 或 GC 差值，必须标记为 **JVM 全局采样变化，不代表该任务自身资源消耗**；并发、GC 和采样时机都会影响数值。不得虚构波动范围、也不根据未经验证的固定阈值判断单个任务内存异常。
- 通过项目所用 Spring 版本的 `ThreadPoolTaskExecutor.getActiveCount()`、`getQueueSize()` 获取池快照；不要使用不存在的直接 `getQueue()` 调用。
- 指标开关、慢请求阈值、日志级别和容量统一配置并提供环境变量示例，不将本机路径写进配置。

## 6. 开发诊断页面与保护

目标包含诊断页面，但它涉及全局日志，不属于普通用户的个人记录功能，不能只靠 `demo` profile 判断权限。

- 采用**独立开发配置**：默认关闭；显式设置开关与独立高强度诊断凭据后才启用，启动时校验配置，生产配置不得启用。默认 Compose 不暴露该功能；文档提供仅本机演示的覆盖配置与启动步骤。
- 凭据通过非提交的环境变量提供，不写进源码、镜像、浏览器包、URL、日志或示例默认值。诊断页面使用专门的短时、HttpOnly、SameSite 的诊断会话，服务端逐请求鉴权；不复用普通访客或账号权限。写操作或会话建立需校验来源及 CSRF 风险；退出及过期后失效。
- 后端只提供受控白名单事件的有界内存缓冲，容量及单条大小可配置；满时明确淘汰最旧事件，不阻塞业务线程。不得将任意原始堆栈、密码或请求体送入页面；生产环境和未开启时接口不可访问。
- 页面支持按 `requestId`、`taskId`、级别和时间查询，明确显示“仅本实例内存记录，重启丢失、不是完整审计”。普通用户页面不显示入口。
- 本机演示应限制绑定地址，且不得把“仅监听 localhost”当成身份鉴权。Next.js 代理、容器网络、跨站请求和未授权访问都要验证；无法可靠实现权限与隔离时，不暴露该页面，并在交付中如实标记未完成。

## 7. 日志保留与查阅

在 Compose 中按需要配置容器日志轮转的大小和数量，并注明依赖所选日志驱动；保留期、容器重建与磁盘限制都要明确。不要使用本机绝对路径，不删除现有数据库和素材卷。

在有 `jq` 的环境中可以按任务查询：

```sh
docker compose logs --no-log-prefix --no-color backend \
  | jq -R 'fromjson? | select(.taskId == "<任务ID>")'
```

`jq` 不是应用运行依赖；无 `jq` 时可直接查看 `docker compose logs --no-color backend`。容器启动横幅或第三方输出可能不是 JSON，需要验证过滤命令。README 应说明如何按编号查找、哪些日志可能因轮转或容器重建而不再存在。

## 8. 实施顺序

### 阶段 A：盘点与契约

1. 清点现有错误码、中文文案、前端分支与历史记录格式，识别安全敏感场景。
2. 编制集中错误目录、旧码映射、可公开文案键与内部 detail；固定兼容规则和中英文翻译范围。
3. 确定配置项及默认值，更新接口文档；先编写现有行为和目录完整性测试。

### 阶段 B：统一错误与 i18n

4. 构建目录读取、代码常量生成／一致性校验、文案解析和回退；实现 Java 只读语言包接口。
5. 逐域迁移账号、模板、素材、任务和通用异常，保留兼容的 code、状态与用户行为。
6. 前端统一解析错误、获取并缓存语言包，保留 requestId；处理语言包失败、网络失败和旧客户端数据。
7. 完成中英文、未知语言、未知 key、参数校验、账号防枚举和现有流程回归测试。

### 阶段 C：历史原因与诊断链路

8. 加入 V8 可空迁移，扩展任务与步骤的安全文案键、可控参数和内部原因；确保事务一致。
9. 兼容旧历史、新任务及旧版回滚；检查个人 API 不返回内部 detail，并验证跨用户隔离。
10. 实现 requestId、结构化日志、异步任务关联与关键事件；排除高频轮询和敏感数据。

### 阶段 D：指标与诊断页面

11. 在任务详情展示阶段耗时；实现可配置 JVM、GC 和线程池快照，明确其全局采样边界。
12. 实现默认关闭、需独立认证和来源校验的诊断接口、有限缓冲和页面；验证关闭及未授权时不可访问。
13. 更新 Compose 非敏感示例、README、部署回滚、日志保留、语言包及隐私说明。

### 阶段 E：验收

## 9. 关键测试与验收标准

- **错误契约**：旧 code、HTTP 状态、`IDENTITY_CHANGED` 等既有分支不回归；中文、英文、缺失翻译、未知 key、语言包请求失败均有安全回退；字典完整且占位符一致。
- **历史与迁移**：空库和 V7 数据升级；旧失败任务、新失败任务均可展示；回滚代码读取旧字段；普通任务接口不返回 `error_detail`。不同账号互相不能读取素材、任务和结果。
- **日志链路**：已受理 HTTP 请求的编号在响应与对应日志一致；任务创建日志能关联 taskId；两个并发任务及线程复用不串 MDC；日志故障不使业务转为成功或失败。
- **隐私**：构造包含手机号、邮箱、验证码、Cookie、密码、文件名、路径的异常和输入，检查普通日志和诊断页面不输出这些内容；不能只测试已经脱敏的接口数据。
- **安全**：登录对外不区分账号不存在和密码错误；越权素材请求保持统一响应；诊断功能默认关闭，错误凭据、普通用户、非允许来源与过期会话均不能读取全局日志。
- **性能与生命周期**：轮询不产生 INFO 洪泛；阶段耗时的缺失／负数／跳过状态正确；指标关闭、采集失败及并发采样不改变任务执行。
- **部署**：空环境 Docker 一键启动、非敏感配置示例、可解析日志及合理轮转；保留原数据库和素材卷。记录只在容器内执行的命令和实际结果。
